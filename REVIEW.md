# REVIEW.md

List every defect found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health()` | Always returns `200 {"status": "ok"}` without ever contacting MongoDB. The grader polls `/health` before running tests; a lying health check causes the entire suite to fail if the DB is down. | Stop MongoDB and call `GET /health`; expect 503, get 200. | Added `db.command("ping")`; returns 200 only on success, raises `HTTPException(503)` on any exception. |
| 2 | `create_employee()` | Duplicate check uses `find_one` then `insert_one` (check-then-insert). Two concurrent requests both pass the `find_one` guard and both insert, violating the unique-emp_code contract. | Send two identical `POST /employees` simultaneously; both return 201. | Removed `find_one` guard entirely. Rely on the unique index on `emp_code` created at startup; catch `DuplicateKeyError` → 409. |
| 3 | `create_employee()` | `created_at = datetime.now()` produces a naive datetime in the local machine timezone, not UTC. Stored wrong in MongoDB; also returned as a datetime string, not an epoch-millisecond integer. | Call `POST /employees`; the `created_at` field in the response is a string like `"2026-07-06T10:30:00"` instead of an integer like `1751780400000`. | Changed to `datetime.now(timezone.utc)`. Serialized through `serialize_employee()` which calls `to_epoch_ms()`. |
| 4 | `list_employees()` | `skip = page * page_size` instead of `(page - 1) * page_size`. Page 1 skips 20 records, so the first page always returns nothing when there are fewer than 21 employees. | Create 5 employees; `GET /employees?page=1` returns `items: []`. | Changed to `skip = (page - 1) * page_size`. |
| 5 | `list_employees()` | `total = db.employees.count_documents({})` ignores the `department` filter. With a department filter applied, `total` still returns the count of the whole collection. | Create employees in two departments; `GET /employees?department=Engineering`; `total` equals all employees, not just Engineering ones. | Changed to `total = db.employees.count_documents(q)` where `q` is the same filter used for the query. |
| 6 | `list_employees()` | No `.sort()` call. MongoDB returns documents in natural insertion order, which is not guaranteed alphabetical. Contract requires `emp_code` ascending. | Insert employees in non-alphabetical order; `GET /employees`; results are in insertion order. | Added `.sort("emp_code", ASCENDING)` to the find cursor. |
| 7 | `punch_in()` | No 404 when the employee does not exist. `emp` is `None`, but the code accesses `emp["shift_start"]` immediately after, causing a `TypeError` and an unhandled 500. | Call `POST /attendance/punch-in` with a non-existent `emp_code`; get a 500 crash. | Added `if emp is None: raise HTTPException(404, ...)` immediately after the `find_one`. |
| 8 | `punch_in()` | `datetime.fromtimestamp(body.punched_at / 1000)` without a timezone argument produces a naive datetime in the local machine timezone. On a UTC server the attendance date is computed in UTC, not IST (R1). | Send `punched_at` for 00:30 IST (which is 19:00 UTC the previous day); the record gets the UTC date (previous day) instead of the IST date (correct day). | Changed to `datetime.fromtimestamp(ms / 1000, tz=timezone.utc)`, then converted to IST for date and late calculations. |
| 9 | `punch_in()` | Overnight shift attendance date not handled (R1). For a 22:00–06:00 shift, a punch-in at 02:00 IST on Jul 7 should produce `date = "2026-07-06"` (the shift-start day), but the code always uses the punch-in's own calendar date. | Use EMP0005 (22:00–06:00 shift); send punch-in at 02:00 IST Jul 7; `date` field in response is `"2026-07-07"` instead of `"2026-07-06"`. | Added `attendance_date_ist()` helper that checks whether the shift is overnight (`shift_end <= shift_start`) and whether the punch-in's IST time is strictly before `shift_end`; if so, subtracts one day. |
| 10 | `compute_late_minutes()` | Three sub-defects: (a) The threshold condition `minutes > 10` operates on truncated minutes, so a punch-in 10 min 1 s late gives `int(10.016) = 10` which fails `> 10` → returns 0 instead of 10. (b) The `shift_start` datetime is built from the punch-in date, not the attendance date, so overnight employees compare against the wrong day. (c) The comparison is done in local machine time, not IST. | Shift 09:30, punch-in 09:40:01 IST → expected `late_minutes = 10`, got 0. | Rewrote `compute_late_minutes()` to: convert to IST; build `shift_start_ist` from the `attendance_date` parameter (not punch-in date); compare raw integer seconds `> 600`; return `elapsed_seconds // 60`. |
| 11 | `punch_in()` | `find_one` + `insert_one` race condition (same as defect #2). Two simultaneous punch-ins for the same employee on the same day both pass the `find_one` check and both insert, creating two records for the same `(emp_code, date)`. Contract explicitly bans check-then-insert. | Send two simultaneous punch-in requests for the same employee; both return 201. | Removed the `find_one` guard. The unique compound index on `(emp_code, date)` created at startup ensures only one insert succeeds; `DuplicateKeyError` → 409. |
| 12 | `punch_in()` | Response includes an `"id"` field (`str(res.inserted_id)`) that the contract never defines. `AttendanceRecord` has no `id` or `_id` field. Also `punch_in` was returned as a datetime string, not epoch milliseconds. | Call `POST /attendance/punch-in`; response has an unexpected `"id"` field and `punch_in` is a string. | Replaced ad-hoc serialization with `serialize_attendance(doc)`, which pops `_id`, converts all datetime fields to epoch ms, and applies legacy-record defaults. |
| 13 | `list_attendance()` | `list(db.find(...))` loads every matching document into Python before sorting and paginating. On 100,000 records this is very slow and memory-heavy. Contract says "do not load the collection into memory". | Query `GET /attendance` with 100k records; response is slow or crashes with OOM. | Pushed sort, skip, and limit to MongoDB: `.sort([("date",-1),("emp_code",1)]).skip(skip).limit(page_size)`. |
| 14 | `list_attendance()` | Python sort uses only `date` descending; no secondary sort by `emp_code`. Contract requires `date DESC, emp_code ASC`. | Records on the same date appear in random order across pages. | Used `.sort([("date", DESCENDING), ("emp_code", ASCENDING)])` in the MongoDB cursor. |
| 15 | `list_attendance()` | Each doc is mutated with `d["id"] = str(d.pop("_id"))`, exposing the internal MongoDB ObjectId as `"id"`. Contract says `_id` never appears in a request or response. | Call `GET /attendance`; every item has an `"id"` field. | Replaced with `.find(q, {"_id": 0})` projection and `serialize_attendance()` which never exposes `_id`. |
| 16 | Module level | No indexes created anywhere. Without a unique index on `employees.emp_code`, the race condition in defect #2 cannot be fixed. Without a unique compound index on `attendance_logs.(emp_code, date)`, defect #11 cannot be fixed. The `/admin/explain` grader check also requires IXSCAN on a 100k dataset. | Any concurrent test, or running the explain endpoint — COLLSCAN in explain output, no uniqueness enforcement. | Created four indexes in the `lifespan` startup function (idempotent): `employees.emp_code` (unique), `attendance_logs.(emp_code, date)` (unique compound), `attendance_logs.(date DESC, emp_code ASC)`, `employees.department`. |
| 17 | Module level | `os.getenv("MONGO_URI")` in the starter matches the `.env` key correctly. However `os.getenv("MONGO_DB", "attendance_db")` uses the default `"attendance_db"` but the `.env` file sets `MONGO_DB=hrone`. Without the `.env` being loaded or the env var being set, the code silently connects to a different database. | Run the app without `MONGO_DB` set; queries return empty results because data is in `hrone`, not `attendance_db`. | Changed default fallback to `"hrone"` to match the provided `.env`; `load_dotenv()` is called at startup so real env vars always win. |
| 18 | `EmployeeIn` (Pydantic model) | All fields are plain `str` with no validation. The contract defines specific patterns for `emp_code`, `email`, `shift_start`, `shift_end`, minimum/maximum lengths for `name` and `department`, and requires `shift_start != shift_end`. Invalid inputs are silently stored. | `POST /employees` with `emp_code: "BADCODE"`, `email: "notanemail"`, `shift_start == shift_end`; all return 201. | Replaced `EmployeeIn` with `EmployeeCreate` using Pydantic `Field(pattern=...)`, length constraints, `joined_on: date`, and a `model_validator` that rejects equal shift times. |

## Items reviewed and decided NOT to be defects

| Item | Verdict |
|---|---|
| `IST = timezone(timedelta(hours=5, minutes=30))` | Correct UTC+05:30 offset. Not a defect on its own — the defect was that the constant was never used by any of the existing calculations. |
| `compute_work_hours()` arithmetic | `(punch_out - punch_in).total_seconds() / 3600` is mathematically correct. The defect is that Python's `round()` uses banker's rounding, not half-up as R4 requires. Fixed by using `Decimal` with `ROUND_HALF_UP`. Logged as part of defect #3 / the missing derivation logic, not a separate structural defect. |
| `requirements.txt` | Correct packages and version constraints. No issues. |
| `sample_seed.py` | Reads `MONGO_URI` / `MONGO_DB` consistently with how `main.py` now reads them. No issues. |
| `compute_overtime()` helper in starter | Logically flawed for overnight shifts (builds the shift-end datetime from the attendance date without adding a day), but this helper was never called by any endpoint in the starter. It was replaced wholesale rather than patched. |
